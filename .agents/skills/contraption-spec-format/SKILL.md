# contraption-spec-format

The canonical artifact: a JSON description of a contraption. Validated
by `pack/src/spec/schema.ts`, dispatched by the pack into block
placements at the player's anchor, snapshotted for undo.

## Transport contract

```
agent / CLI  --HTTP-->  forge daemon  <--HTTP-- pack (outbound)
```

All requests carry header `X-Forge-Token: <token>`. The token lives in
`.env` (host) and `<bds>/config/<pack-uuid>/secrets.json` (pack),
generated by `tools/pack-deploy.ps1` on first deploy.

| Method | Path         | Caller | Body                                  | Response                                                                                                       |
| ------ | ------------ | ------ | ------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| POST   | `/heartbeat` | pack   | `{ timestamp, packVersion, anchor }`  | `{ ok: true }`                                                                                                  |
| POST   | `/poll`      | pack   | `{}`                                  | `{ commands: [{ jobId, type, payload }, ...] }`                                                                |
| POST   | `/result`    | pack   | `{ jobId, result }`                   | `{ ok: true }`                                                                                                  |
| POST   | `/build`     | agent  | `{ spec: <ContraptionSpec> }`         | blocks ≤30s; `{ ok: true, data: { jobId, name, placed, bounds } }` or `{ ok: false, error, errors? }`           |
| POST   | `/undo`      | agent  | `{ jobId?: string }`                  | blocks ≤30s; `{ ok: true, data: { jobId, name, restored } }` or `{ ok: false, error }`                          |
| GET    | `/health`    | agent  | —                                     | `{ ok, anchor, packVersion, lastHeartbeat, heartbeatCount, daemonStartedAt, pendingCommands, awaitingResults }` |
| GET    | `/anchor`    | agent  | —                                     | `Anchor \| null`                                                                                                |
| POST   | `/echo`      | agent  | any string                            | `{ echo: <body> }`                                                                                              |

Pack polls every 5 ticks (≈250ms). End-to-end latency for `/build` is
roughly one poll interval plus the build itself — typically <500ms.

## Schema (Phase 3)

```jsonc
{
  "name": "lever-wire-lamp",      // required, kebab/snake identifier
  "version": 1,                    // optional, positive integer
  "footprint": { "size": [3, 1, 1] }, // required, positive [x, y, z]
  "anchor": "player-facing",       // "absolute" | "player-facing"; default "absolute"
  "blocks": [
    {
      "at": [0, 0, 0],             // integer [x, y, z] local to anchor
      "id": "minecraft:lever",     // must be in components allow-list
      "states": {                  // optional, schema per-component
        "lever_direction": "down_east_west",
        "open_bit": false
      }
    }
  ]
}
```

### Field semantics

- **`name`**: identifier, regex `^[a-z0-9][a-z0-9\-_]*$/i`. Used as
  filename when saved to `specs/`.
- **`footprint.size`**: bounding box dimensions. Every block in
  `blocks[].at` must satisfy `0 ≤ at[i] < size[i]`. The validator
  enforces this.
- **`anchor`**:
  - `"absolute"`: block absolute position is `(anchor.pos[i] + at[i])`.
    No rotation applied. Directional state values are passed through
    unchanged. Use this when you want world-frame coordinates.
  - `"player-facing"` (Phase 4a, recommended for new specs): local
    `+X` axis is rotated to point "in front of the player" (the
    direction `anchor.facing` records). Positions AND directional
    block state values rotate together so the whole contraption
    stays self-consistent.

    The rotation step is `0` (identity) when `anchor.facing === "east"`,
    `1` (90° CW) for `"south"`, `2` (180°) for `"west"`, `3` (270° CW)
    for `"north"`. The math lives in `pack/src/world/transform.ts`
    and has unit tests at `test/transform.test.ts` — `npm test`.
- **`blocks[].id`**: must be in
  [`pack/src/spec/components.ts`](../../pack/src/spec/components.ts).
  See `redstone-components-reference` skill for the live list.
- **`blocks[].states`**: optional. Pass-through to
  `BlockPermutation.resolve`. Only state keys whitelisted for the
  component are accepted; values are forwarded as-is and Bedrock
  validates them.

### Hard rules

1. Spec must declare every block ID in the components allowlist. If
   you want a component that isn't there, ASK the user before adding
   it — `pack/src/spec/components.ts` is the source of truth and
   needs human review.
2. `at` coordinates must be integers.
3. `states` keys must be in the component's `stateKeys` list.
4. The footprint must enclose every block.

## Worked example

```jsonc
// specs/examples/lever-wire-lamp.json
{
  "name": "lever-wire-lamp",
  "version": 1,
  "footprint": { "size": [3, 1, 1] },
  "anchor": "player-facing",
  "blocks": [
    { "at": [0, 0, 0], "id": "minecraft:lever" },
    { "at": [1, 0, 0], "id": "minecraft:redstone_wire" },
    { "at": [2, 0, 0], "id": "minecraft:redstone_lamp" }
  ]
}
```

With `anchor: "player-facing"`, the lever lands at the anchor block and
the wire + lamp extend "in front of" whichever cardinal direction the
player faced when they ran `/rsforge:anchor`. The selftest verifies all
four facings (`east`, `south`, `west`, `north`).

Deploy via CLI:

```pwsh
# Set anchor in-game with /rsforge:anchor (or, for selftest:
# /scriptevent rsforge:debug_setanchor 4 70 4 north)
node tools/forge.mjs build specs/examples/lever-wire-lamp.json
# -> { "ok": true, "data": { "jobId": "...", "placed": 3, "bounds": {...}, "rotationSteps": 0|1|2|3 } }

# Undo it
node tools/forge.mjs undo
# -> { "ok": true, "data": { "jobId": "...", "restored": 3 } }
```

## What lands in later phases

- **Phase 4b**: `ports` — named inputs (lever, button,
  pressure_plate, redstone_block) and outputs (lamp, piston,
  comparator, observer) with their positions. Required for any
  `tests` to address them.
- **Phase 4b**: `tests` — declarative test sequences (`set`,
  `wait_ticks`, `expect`) executed by a new `POST /test` endpoint.
  See `contraption-testing` skill.
- **Phase 4b**: `POST /redo`, `GET /world?bounds=...`, in-game
  `/rsforge:undo|redo|history` slash commands.
- **Phase 6**: `includes` — compose patterns from `patterns/` at a
  local offset.

## Common failure modes

| Symptom | Cause |
| ------- | ----- |
| `/build` returns `{ ok: false, error: "spec validation failed", errors: [...] }` | Schema violation. The `errors` array has `path` + `message`. Fix the spec and retry. |
| `/build` returns `{ ok: false, error: "no anchor set..." }` | The pack has no anchor recorded. Run `/rsforge:anchor` in-game (or fire `rsforge:debug_setanchor` via the selftest harness). |
| `/build` returns `{ ok: false, error: "build failed: block X at Y: ... InvalidArgumentError" }` | Bedrock rejected a block state. Re-run `tools/discover-states.mjs` for that block id and update the spec's `states` to match what BDS actually accepts. |
| `/build` returns `504 pack did not return a result within 30000ms` | Pack didn't poll (daemon was started after BDS — wait for first /poll), or pack is hung. Check BDS logs for `[rsforge]` errors. |
| Spec passes validation but blocks land in the wrong place | Anchor's `pos` is unexpected. `GET /anchor` to confirm before debugging the spec. |
